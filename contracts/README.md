# Contracts between Chaos Garden services

## `request-event.v1`

The event the proxy (chaos-garden-proxy) publishes for every proxied request, and the ingest service (`ingest/`) consumes from the Redis Stream `chaos:requests` (one field, `data`, holding the JSON).

| File | Purpose |
|---|---|
| `request-event.v1.schema.json` | The contract, as JSON Schema (draft 2020-12). |
| `fixtures/valid/*.json` | Events every consumer must accept. |
| `fixtures/invalid/*.json` | Events every consumer must reject (they go to the dead-letter stream). |
| `manifest.json` | SHA-256 of every file above, generated by `build-manifest.mjs`. |

**This repo holds the source of truth.** chaos-garden-proxy keeps a copy in its own `contracts/` folder; its CI compares that copy's manifest with this one on `main` and fails if they differ.

### How it is enforced

- **Consumer (ingest):** `ingest/src/stream/contract.spec.ts` checks that the ingest parser and the schema agree on every fixture: valid ones are accepted by both, invalid ones rejected by both.
- **Producer (proxy):** its e2e tests validate the events the proxy really emits against the schema, strictly (no undocumented properties).
- **Copies in sync:** `npm run contract:check` in chaos-garden-proxy (also in its CI).

### Changing the contract

1. **Adding an optional property** (allowed within v1): add it to the schema, add or update a fixture, then run `node contracts/build-manifest.mjs`. Consumers already ignore unknown properties, so you can release the consumer and producer in any order. Then run `npm run contract:sync` in chaos-garden-proxy.
2. **Anything else** (removing or renaming a property, changing a type, making a property required): that is a new version. Add `request-event.v2.schema.json`, teach the ingest service to accept both versions, release it, then switch the proxy to v2, and only later drop v1.

CI fails if `manifest.json` doesn't match the files (`node contracts/build-manifest.mjs --check`).
